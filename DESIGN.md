# DESIGN.md: Architecture and Engineering Decisions

## 1. How login and the two roles work
Self-signup via [server/src/routes/auth.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/routes/auth.js) exclusively creates accounts with role `customer`. The Zod signup schema in [server/src/rules/validation.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/rules/validation.js) strictly omits the `role` key, ensuring client-supplied role values are stripped before persistence. The `studio` admin account is never registered via the API; it is provisioned exclusively by [server/scripts/seed.js](file:///D:/Art%20studio%20gdgc/art-studio/server/scripts/seed.js) with a bcrypt-hashed password on initial insert. Authentication is centralized in [server/src/middleware/authenticate.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/middleware/authenticate.js), which extracts the JWT from an httpOnly cookie and reloads the user document from MongoDB on every request so privilege revocations take immediate effect. Authorization boundaries use `requireRole("customer")` and `requireRole("studio")` returning 403 on role mismatch, while object-level access is gated by `findOwned()` in [server/src/services/common.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/services/common.js), returning 404 whenever a customer attempts to query another customer's record to avoid existence leakage.

## 2. Why MongoDB Atlas, document models, and indexes
MongoDB Atlas provides a hosted replica set supporting multi-document ACID transactions, required for atomic state swaps between paintings and orders. The domain exhibits natural document cohesion: orders, wall bookings, and pottery requests embed their complete audit history timelines (`history[]`) within the parent document, allowing single-roundtrip reads without relational joins. The critical uniqueness invariants are declared in [server/src/models/Order.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/models/Order.js) as a unique partial index on `{ painting: 1 }` where `{ status: "placed" }`, and in [server/src/models/WallBooking.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/models/WallBooking.js) as a unique partial index on `{ date: 1 }` where `{ status: { $in: ["requested", "confirmed"] } }`. Query performance is backed by compound indexes `{ customer: 1, createdAt: -1 }` and `{ status: 1, createdAt: -1 }`. All indexes are built explicitly via `Model.init()` at server startup and verified against Atlas via [server/scripts/verify-indexes.js](file:///D:/Art%20studio%20gdgc/art-studio/server/scripts/verify-indexes.js).

## 3. Stopping double-selling and double-booking
Double-selling is prevented through a three-layer defense in [server/src/services/orders.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/services/orders.js). Inside `session.withTransaction`, an atomic conditional update `Painting.findOneAndUpdate({ _id, status: "available" }, { $set: { status: "sold" } }, { new: true, session })` claims the painting; if no document is modified, the handler checks if the current caller already holds a `placed` order (returning the existing order idempotently) or throws 409 `PAINTING_ALREADY_SOLD`. The order document is created within the same transaction, and the database-level partial unique index on `{ painting: 1 }` acts as the backstop. Double-booking in [server/src/services/bookings.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/services/bookings.js) is guarded by the unique partial index on booking dates: concurrent insert attempts collide on the unique index, and MongoDB duplicate key error 11000 is mapped by [server/src/middleware/errorHandler.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/middleware/errorHandler.js) to 409 `DATE_TAKEN`. When a booking transitions to `declined` or `cancelled`, it falls out of the partial index filter, atomically freeing the date. These guarantees were verified against Atlas with zero 5xx errors via [server/tests/concurrency.test.js](file:///D:/Art%20studio%20gdgc/art-studio/server/tests/concurrency.test.js) and the 20-client stress runner [server/scripts/race-test.js](file:///D:/Art%20studio%20gdgc/art-studio/server/scripts/race-test.js).

## 4. What was finished, left out, and next steps
Every P0 and P1 requirement in the brief was built and tested: customer and studio auth flows, painting purchase/cancellation, race-safe wall booking calendar with availability lookups, pottery custom request queues with studio approval, centralized error contracts, request IDs, rate-limited login, origin validation, idempotent seeding, and the React frontend with `<AsyncState>` and helpful refusals. The test suite verified 168 tests across 6 files, and a reversible mutation check confirmed that removing the conditional update breaks the concurrency guarantees as expected. Left out: real payment processing, email notifications, image file uploads, and pagination on admin tables (omitted per brief section 13 scope limits). If extending the system in production, next steps would be introducing Redis-backed distributed rate limiting, webhook dispatch for order notifications, and database read-replicas for catalog browsing.

## Interpretations & Rules
- **Calendar & Timezone**: All dates are formatted as `YYYY-MM-DD` and validated as real calendar dates (rejecting impossible dates like `2026-02-30`). Day differences and relative cutoffs are calculated strictly against Indian Standard Time (`Asia/Kolkata`) via Luxon in [server/src/rules/dates.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/rules/dates.js), avoiding millisecond rounding errors.
- **Booking & Cutoff Windows**: Wall bookings require `7 <= daysUntil <= 90`. Pottery needed-by dates require `daysUntil >= 14`. Wall booking cancellations are allowed only when `daysUntil >= 3`; cancellations attempted fewer than 3 days prior fail with 409 `CANCELLATION_WINDOW_CLOSED`.
- **Currency & Money**: Stored as safe positive integers in INR. Wall painting prices are computed authoritatively on the server (`wallSqFt * 150`) and stored alongside the snapshot rate. Pottery requests carry no pricing.
- **Legal State Transitions**: Managed by a single transition table in [server/src/rules/transitions.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/rules/transitions.js):
  - Order: `placed -> cancelled` (customer owner only).
  - Booking: `requested -> confirmed | declined` (studio); `requested | confirmed -> cancelled` (customer owner, if `daysUntil >= 3`).
  - Pottery: `requested -> accepted | declined` (studio); `requested -> cancelled` (customer owner). Editable via PATCH only while `requested`.

## CSRF & Origin Stance
Authentication cookies use `SameSite=Lax` and `httpOnly`. In addition, [server/src/middleware/originCheck.js](file:///D:/Art%20studio%20gdgc/art-studio/server/src/middleware/originCheck.js) inspects mutating HTTP methods (`POST`, `PATCH`, `PUT`, `DELETE`): if an `Origin` header is present, it must match the request host, returning 403 `FORBIDDEN` on cross-origin mismatches. Requests without Origin headers (such as API integration tests and cURL) are permitted.

## Security Controls & Limitations
- **Controls**: Strict Zod schemas sanitize all request bodies, route params, and query strings. The error handler suppresses stack traces and database internal diagnostics in client responses. Login attempts are throttled by `express-rate-limit` (10 per 15 minutes per IP).
- **Limitations**: Rate limiter state is stored in-process memory. Static images served under `/images` are unauthenticated public assets. JWT invalidation relies on client cookie clearing or deleting the user document from the database.

## Known Issues
None. All 168 tests, index verifications, idempotent seeds, race checks, and client production builds pass cleanly against the live MongoDB Atlas cluster.
